# Установка

English: [../installation.md](../installation.md)

Впервые работаете с сервером? Начните с [руководства для новичков](beginners.md).

## Установка одной командой

На чистом сервере, от root:

```bash
curl -fsSL https://raw.githubusercontent.com/qklafk/netoryx/main/install.sh | sudo bash
```

Установщик спрашивает токен бота (от @BotFather) и ваш Telegram ID, ставит Docker, собирает стек в `/opt/netoryx`, ждёт
HTTPS и печатает одноразовую ссылку на веб-админку. Без домена используется `<ip-with-dashes>.sslip.io`, для которого не
нужна настройка DNS. Неинтерактивный вариант:

```bash
sudo bash install.sh --bot-token <token> --admin-id <telegram id> [--domain <name>]
  [--panel xui|remnawave|marzban|pasarguard|marzneshin|none] [--with-tgproxy] [--with-socks] [--socks-port 2080] [--yes]
```

| Параметр | Значение |
| --- | --- |
| `--panel NAME` | VPN-панель для установки, по умолчанию `xui`: `xui`, `remnawave`, `marzban`, `pasarguard`, `marzneshin` или `none` (см. [Выбор панели](#выбор-панели)). Каждая получает случайные учётные данные администратора и точку входа VLESS + Reality, делящую порт 443 |
| `--with-xui` | то же, что `--panel xui` |
| `--with-tgproxy` | устаревшее: установить MTProto-прокси для Telegram (telemt), он тоже работает на 443; в некоторых странах не работает, по умолчанию не предлагается |
| `--with-shadowsocks` | добавить VPN-инбаунд Shadowsocks-2022 на порт `--ss-port` (по умолчанию 8388, tcp+udp); только 3x-ui. Shadowsocks не использует TLS, поэтому не может делить 443 и требует отдельного порта; считайте его запасным протоколом, так как некоторые сети фильтруют полностью зашифрованный трафик. Пропускается с уведомлением, если эта версия не умеет его создавать |
| `--with-socks` | устаревшее: создать прокси SOCKS5 для Telegram на `--socks-port` (по умолчанию 2080); только 3x-ui; по умолчанию не предлагается |
| `--tg-domain` | TLS-имя, которое имитирует MTProto-прокси (по умолчанию `petrovich.ru`) |
| `--brand-name` | название вашего сервиса, которое видят клиенты (по умолчанию `VPN`) |
| `--lang ru\|en` | язык сообщений установщика |
| `--no-firewall` | не трогать ufw / firewalld |
| `--force-os` | попробовать операционную систему, которой нет в списке ниже, на свой риск |
| `--update` | загрузить последний релиз и перезапустить только приложение |
| `--dry-run` | напечатать план и ничего не менять |

Если у вас свой домен, до запуска установщика создайте A-записи для `<domain>` и (с `--with-xui`) `vpn.<domain>`, указывающие
на сервер; установщик предупредит, если они не разрешаются.

### О чём спрашивает установщик

Интерактивный режим объясняет каждый вопрос на вашем языке (по-русски, если `LANG` начинается с `ru`, иначе по-английски;
язык можно задать флагом `--lang ru|en`), сразу проверяет ответ и спрашивает снова, если он неверен. Enter принимает
значение в скобках; в вопросах да/нет показывается `[Y/n]`.

1. Токен бота: от @BotFather (`/newbot`), проверяется через Telegram. Если Telegram недоступен, установщик предупредит и пойдёт дальше.
2. Ваш Telegram ID: число, которое отвечает @userinfobot.
3. Домен: нажмите Enter, чтобы использовать бесплатный адрес `<ip-with-dashes>.sslip.io`. Домен, не указывающий на этот сервер, отклоняется с предложением использовать sslip.io.
4. Название сервиса (`BRAND_NAME`, по умолчанию `VPN`): имя, которое клиенты видят в боте, Mini App и своих приложениях. Позже его можно изменить в админке; `--brand-name` задаёт его без вопроса.
5. Какая VPN-панель: нумерованный список с однострочным описанием каждой (Enter = 3x-ui, последний пункт - «без панели, подключу свою позже»).

Установка состоит из девяти пронумерованных шагов, каждый завершается галочкой. Если шаг не удался, установщик назовёт его,
журнал (`/var/log/netoryx-install.log`) и команду для повторного запуска; повторять всегда безопасно. В конце сводка
показывает одноразовую ссылку на админку, бота, адрес подписок, общую ссылку на Telegram (страница `/tg`, ссылка подписки, QR-код; см. [telegram-only.md](telegram-only.md)), где хранятся учётные данные (только пути), как открыть
панель через SSH-туннель, следующие шаги и команды `netoryx`. `--yes` отключает все вопросы для автоматизации (значения тогда
берутся из флагов).

### Поддерживаемые системы

Ubuntu 22.04, 24.04 и 26.04; Debian 12 и 13; AlmaLinux 9 и Rocky Linux 9; на x86_64 и aarch64. Не менее 2 vCPU, 2 ГБ ОЗУ
(при менее чем 4 ГБ создаётся файл подкачки 2 ГБ) и 10 ГБ свободного места на диске. Другие системы отклоняются, если не
указан `--force-os`.

Чем отличаются системы:

- Пакеты: `apt` в Debian и Ubuntu, `dnf` в AlmaLinux и Rocky (`qrencode`, нужный для QR-кода в терминале, там берётся из EPEL и
  необязателен).
- Docker CE ставится из официального репозитория Docker (`download.docker.com/linux/ubuntu`, `/debian`; репозиторий CentOS
  для AlmaLinux и Rocky, которые двоично с ним совместимы). Кодовое имя репозитория читается из `/etc/os-release`.
- Брандмауэр: `ufw` в Debian и Ubuntu, `firewalld` в AlmaLinux и Rocky. Порты SSH из конфигурации sshd (и тот, через который
  вы подключены) всегда остаются открытыми вместе с 80, 443 и (только если вы включили устаревший прокси SOCKS5) его портом. Контейнеры должны достучаться до панели (3x-ui,
  сеть хоста) и до порта бэкенда Reality на хосте: с ufw диапазону `172.16.0.0/12` разрешены только эти два порта; с
  firewalld этот диапазон помещается в зону `trusted` (сопоставление идёт по адресу источника, поэтому работает в какой бы
  зоне Docker ни создал мосты), а после изменения правил Docker перезапускается. Порты, публикуемые Docker, обходят оба
  брандмауэра по замыслу; стек публикует только 80 и 443.
- SELinux (AlmaLinux, Rocky): bind-монтирования в `docker-compose.yml` имеют метку `:z`, поэтому стек работает при
  включённом SELinux; отключать ничего не нужно.

### Управление установкой

```bash
netoryx status | logs [service] | update | backup | admin-link | tg-link | restart [service] | uninstall [--purge]
```

`netoryx update` загружает новый релиз и пересобирает только приложение, поэтому VPN-соединения не прерываются. Он сообщает,
когда изменились `edge`, Caddy или конфигурация панели и нужен перезапуск (`netoryx restart edge caddy`). Повторный запуск
`install.sh` на существующей установке обновляет или чинит её: созданные секреты сохраняются, тома никогда не стираются.
`netoryx uninstall` останавливает стек и сохраняет данные; `--purge` дополнительно удаляет тома, код и секреты.

Созданные учётные данные лежат в `/root/netoryx` (режим 0600): `xui-credentials` и `telemt-credentials`. Журнал установщика -
`/var/log/netoryx-install.log`; секретов в нём нет.

### Установка проверенного релиза

Команда выше ставит самый свежий код из ветки `main`. Чтобы установить зафиксированный релиз и проверить файл перед
запуском, скачайте установщик и контрольные суммы со [страницы релизов](https://github.com/qklafk/netoryx/releases):

```bash
curl -fsSLO https://github.com/qklafk/netoryx/releases/latest/download/install.sh
curl -fsSLO https://github.com/qklafk/netoryx/releases/latest/download/SHA256SUMS
sha256sum --ignore-missing -c SHA256SUMS && sudo bash install.sh
```

Установщик из релиза ставит код этого релиза. `netoryx update` потом переходит на новейшую версию; чтобы остаться на
релизе, запускайте `sudo NETORYX_REF=<тег> netoryx update`.

## Дополнительно: ручная настройка

Остальная часть страницы описывает то, что автоматизирует установщик, для тех, кто предпочитает всё настраивать вручную.

## Требования

- Поддерживаемая система (см. выше); лучше всего проверена Ubuntu Server 24.04 LTS x86_64.
- 2 vCPU, 2 ГБ ОЗУ и 60 ГБ SSD для небольшой установки «всё на одном сервере».
- SSH-доступ, который сохраняется, пока планируются изменения брандмауэра.
- Домен и публичная точка HTTPS нужны только для возможностей, которые их требуют, таких как Telegram Mini App и некоторые
  платёжные вебхуки.

## Планирование режимов

Установщик рассматривает эти настройки независимо:

- Профиль продукта: `personal` или `commercial`.
- Роль развёртывания: `all-in-one`, `control-plane` или `vpn-node`.

`personal` не накладывает ограничений на число пользователей или нод. Он лишь не включает коммерческие возможности по
умолчанию. `commercial` - заготовка для работы с подписками; оба профиля используют одно и то же приложение и базу.

Запустите план, не изменяющий систему:

```bash
uv run python -m installer plan --profile personal --deployment-role all-in-one
```

Запустите предварительную проверку для конфигурации ноды:

```bash
uv run python -m installer preflight --profile commercial --deployment-role vpn-node --module proxy.mtproxy
```

Команды проверяют локальный CPU, память, свободное место на диске и требования выбранных портов. Они выводят план в JSON и
возвращают ненулевой код при невыполненных требованиях. `plan` сохраняет возобновляемое состояние выбора без секретов в
`.installer-state.json`.

## Ядро и доверенные модули

Минимальное ядро не зависит от Telegram, веб-интерфейса и коммерческих компонентов. По умолчанию оно хранит только состояние
жизненного цикла модулей в отдельной базе SQLite:

```bash
uv run python -m app core status
uv run python -m app module list
uv run python -m app module install system.demo
uv run python -m app module configure system.demo --set label=example
uv run python -m app module enable system.demo
uv run python -m app module health system.demo
```

На этом этапе доступны только доверенные модули, входящие в релиз. Манифест декларативный и не может выполнять команды
оболочки. Отключение или удаление модуля сохраняет его данные, если явно не указан `--purge-data`.

## Модули, зависящие от HTTPS

Telegram Mini App требует и `interface.telegram-bot`, и публичную точку HTTPS. Объявляйте её, только когда HTTPS-адрес
уже доступен:

```bash
uv run python -m installer plan --profile commercial --deployment-role control-plane \
  --module interface.miniapp --public-https
```

Способы оплаты оцениваются по отдельности на более позднем этапе установки: платёжная система с вебхуками требует доступного
адреса, а офлайн/ручной вариант может не требовать.

## Модель безопасности для будущих операций применения

Будущие операции применения будут требовать проверенный план, резервную копию перед опасными изменениями, проверки
состояния, возобновляемое состояние и откат там, где это технически возможно. Артефакты релиза должны подтверждаться
доверенной подписью или проверкой открытого ключа; контрольная сумма, загруженная из того же недоверенного места, не
доказывает подлинность.

VPN-ноды получат только минимальную среду выполнения ноды и выбранные сетевые службы. Они не получат базу данных
управляющего узла, платёжные службы и полный бэкенд приложения.

## Стек Docker Compose и сетевая схема

`docker-compose.yml` запускает приложение, PostgreSQL, Caddy (автоматический HTTPS) и `edge` - HAProxy, владеющий единственным
публичным TLS-портом 443. HAProxy читает имя сервера каждого TLS-соединения и передаёт его дальше без изменений:

- имена из `deploy/haproxy/sni.map` уходят в VPN (`reality`, инбаунд Reality панели на `REALITY_PORT`) или в прокси для
  Telegram (устаревший, `tgproxy`);
- любое другое имя уходит в Caddy, который отдаёт веб-админку, Mini App и ссылки подписок.

Держать всё на 443 важно: некоторые сети отбрасывают или замедляют трафик на нестандартных портах. В брандмауэре открывайте
только 22, 80 и 443; порты панелей остаются закрытыми, к ним обращаются через сеть Docker или SSH-туннель.

Сначала скопируйте `deploy/haproxy/sni.map.example` в `deploy/haproxy/sni.map` (установщик создаёт этот файл для каждого
сервера сам). Необязательные службы включаются профилями: `--profile xui` (3x-ui в сети хоста) и `--profile tgproxy`
(telemt, устарел). Задайте `DOMAIN`, `SECRET_KEY` и `POSTGRES_PASSWORD` в `.env`; без домена сразу работает
`<ip-with-dashes>.sslip.io`. Первый сертификат может прийти через минуту-две.

### Reality на собственном имени

Направьте инбаунд Reality на встроенный сайт `vpn.<DOMAIN>` (Caddy отдаёт его на `127.0.0.1:8444`): используйте
`vpn.<DOMAIN>` как имя сервера и `127.0.0.1:8444` как назначение, а `vpn.<DOMAIN> reality` добавьте в
`deploy/haproxy/sni.map`. Тогда имя, сертификат и адрес сервера совпадают, что проверяют некоторые сети.

### Сети, отбрасывающие большие TLS-рукопожатия

Некоторые сети отбрасывают второй TCP-сегмент большого TLS ClientHello. Отпечаток Chrome с постквантовой частью ключа даёт
такое приветствие, и VPN «подключается», но трафик не идёт. `REALITY_COMPACT_HELLO` (по умолчанию включён) заставляет ссылки
Reality просить у клиентов отпечаток Firefox без постквантовой части, и приветствие умещается в один сегмент.
Переопределение у эндпоинта в админке по-прежнему приоритетнее.

### Приватность

`CLIENT_IP_LOGGING=off` (по умолчанию) не пускает IP-адреса клиентов в логи и базу; лимиты частоты запросов по-прежнему
работают в памяти. Лимиты устройств для 3x-ui считает бот по HWID, который присылают клиентские приложения
(`XUI_DEVICE_LIMIT=hwid`), поэтому журнал доступа Xray, куда попадали бы IP и посещённые сайты, можно держать выключенным.

### Прокси для Telegram (устарело)

Устаревшая необязательная функция: такие прокси могут не работать в некоторых странах и по умолчанию не ставятся. Актуальный способ
дать людям доступ к Telegram - общая [ссылка доступа к Telegram](telegram-only.md); установщик в конце печатает её страницу `/tg`,
ссылку и QR-код (`netoryx tg-link` напечатает снова).

- MTProto (`--profile tgproxy`, telemt): собственного публичного порта нет. Внесите его `tls_domain` в
  `deploy/haproxy/sni.map` как `tgproxy` и оставьте в его конфигурации `public_port = 443`, чтобы ссылки указывали на 443.
- SOCKS5: создайте `mixed`-инбаунд 3x-ui с парольной аутентификацией на отдельном порту (SOCKS5 не использует TLS и не может
  делить 443), откройте этот порт в брандмауэре, затем отметьте инбаунд в админке как инбаунд SOCKS5 для Telegram и задайте
  публичные хост и порт в параметрах панели. Каждый пользователь получает личные логин и пароль.
  См. [telegram-proxy.md](telegram-proxy.md).

### Блокировка рекламы и трекеров

`ADBLOCK_ENABLED` добавляет правило маршрутизации Xray, отправляющее `geosite:category-ads-all` в blackhole-аутбаунд на каждом
сервере 3x-ui. Включение и выключение перезапускает Xray, поэтому активные VPN-сессии переподключаются. Реклама внутри видео
YouTube отдаётся с тех же хостов, что и сами видео, и таким способом заблокирована быть не может.

### Выход для YouTube

`YOUTUBE_EXIT_ENABLED` вместе с `YOUTUBE_EXIT_LINK` (ссылка `vless://`, `socks5://` или `ss://` другого сервера) направляет
домены из `YOUTUBE_EXIT_DOMAINS` (по умолчанию `geosite:youtube`) через этот сервер на каждой панели 3x-ui, так что YouTube
выходит из страны, где он не показывает рекламу. Всё остальное выходит как прежде. Бот добавляет аутбаунд `youtube-exit`,
балансировщик с проверкой observatory и одно правило маршрутизации, стоящее после правила блокировки рекламы; если выход
недоступен, YouTube переходит на аутбаунд `direct` панели. Также включается определение доменов (sniffing: http, tls, quic)
на VLESS-инбаундах, которое нужно для маршрутизации по доменам. Какие страны не показывают рекламу, со временем меняется, так
что способ может перестать работать. При изменении настройки Xray перезапускается один раз.

| --- | --- | --- |

| Remnawave (`remnawave`) | `remnawave/backend:3.4.10` с PostgreSQL 18 и Valkey, нода `remnawave/node:3.4.5`; регистрирует первого администратора и API-токен, создаёт профиль конфигурации с инбаундом Reality, ноду, хост и добавляет инбаунд в первый внутренний сквад | проверена на живом сервере |

| PasarGuard (`pasarguard`) | `pasarguard/panel:v5.6.0` и `pasarguard/node:v0.5.7`; учётная запись владельца и сертификат ноды создаются автоматически, затем через API конфигурация ядра, группа, нода, хост и API-ключ | проверена на живом сервере |
| Marzneshin (`marzneshin`) | `dawsh/marzneshin:v0.7.4` и `dawsh/marznode:v0.5.7` с более новым ядром Xray; администратор через `marzneshin-cli`, конфигурация Xray с инбаундом Reality для ноды, нода, хост и сервис через API | проверена на живом сервере |
| нет (`none`) | устанавливает только Netoryx; свою панель добавьте в веб-админке (Servers). Так подключается Hiddify: он занимает весь сервер и порт 443, поэтому не может делить хост с этим стеком | - |

Все пять панелей были установлены этим установщиком и проверены от начала до конца настоящим клиентом через порт 443.

Кроме 3x-ui, панели работают в той же сети Docker, что и стек, а не в сети хоста, как в их собственных compose-файлах, поэтому
ничего из них наружу не публикуется: бот обращается к API по имени контейнера, HAProxy доходит до инбаунда Reality по имени
контейнера, а Reality заимствует сайт `vpn.<domain>` Caddy (`caddy:8444`). Файлы лежат в `deploy/panels/<name>/`; `COMPOSE_FILE`
в `.env` выбирает их, поэтому каждая команда `docker compose` (и `netoryx`) видит панель. Логин и пароль администратора -
в `/root/netoryx/<panel>-credentials`; интерфейс панели слушает только `127.0.0.1` (открывайте через `ssh -L` или
опубликуйте, как описано ниже). Теги образов закреплены; обновляйте их в `deploy/panels/<name>/compose.yml` осознанно.

Ограничения с другими панелями: общая ссылка доступа к Telegram работает со всеми панелями, кроме Hiddify; устаревший SOCKS5 для Telegram и Shadowsocks-2022 требуют 3x-ui и пропускаются с уведомлением;
блокировка рекламы и выход для YouTube переписывают шаблон Xray в 3x-ui и работают только с ним; MTProto-прокси (telemt)
работает с любой панелью. Компактное приветствие клиента Reality (`REALITY_COMPACT_HELLO`) применяется к ссылкам 3x-ui; для
остальных панелей установщик задаёт отпечаток `firefox` в создаваемом им хосте. Дополнительным инбаундам на других портах
нужен опубликованный порт в compose-файле панели.

Shadowsocks-2022 (`--with-shadowsocks`) необязателен и в некоторых сетях может работать ненадёжно; рекомендуемый вариант по
умолчанию - VLESS Reality на 443.

Let's Encrypt выдаёт не более 5 сертификатов на одно точное имя в неделю. `netoryx uninstall --purge` удаляет сертификаты,
поэтому многократная переустановка подряд может упереться в лимит, и HTTPS не поднимется, пока он не сбросится. Используйте
собственный домен или не делайте повторных `--purge`.

### Публикация интерфейса панели

Порты панелей остаются закрытыми. Чтобы открыть интерфейс панели в браузере, скопируйте
`deploy/caddy-sites/panel.caddy.example` в `panel.caddy`, укажите апстрим для вашей панели (файл перечисляет их) и пересоздайте
Caddy: интерфейс станет доступен по HTTPS на `https://panel.<DOMAIN>/` (для 3x-ui - с добавлением её веб-пути). Используйте
надёжный пароль и двухфакторную аутентификацию панели.

### Перезапуски

Переразвёртывание только приложения (`docker compose up -d --build --no-deps app`) VPN-сессии не прерывает.
Перезапуск `edge`, `caddy` или панели рвёт открытые соединения; большинство клиентов переподключаются, некоторым нужно
выключить и включить VPN.
